## Gates before another model call

1. **Freeze a new candidate.** Bind the executable/version, harness and contract hashes, effective process/session configuration, actual hook discovery source and hash, permitted tool identity/arguments, fictional fixture and expected outcomes. Preserve old artifacts. Reconcile the current worktree and instructions. Use a fresh output location with exclusive creation and private permissions. Require separate independent requirements and engineering reviews of this exact candidate, including source evidence for enforcement.
2. **Establish prevention.** Identify a supported boundary that rejects every unapproved tool *before* its handler or discovery runs. It must cover built-ins, dynamic tools, aliases/namespaces, parallel calls, hosted/specialized tools and calls made after compaction. A client callback only covers tools actually dispatched to that callback. Prompt-only restrictions, metadata declarations and hook success on the happy path are insufficient.
3. **Verify failure behavior without live services.** In a fake-only environment with no real data or service reachability, attempt the forbidden built-in listing, an unknown tool, namespace/alias variations, duplicate and concurrent reads, wrong session/turn/arguments, and calls before the continuation. Exercise absent/malformed policy, dispatcher failure, timeout and interrupted validation. Require rejection before an instrumented handler/discovery counter changes. A stand-alone mock validates the mock only; bind the eventual proof to the real dispatch implementation and exact executable. If that binding or containment is unavailable, leave this gate open and do not run the recovery test.
4. **Verify current preconditions.** Recheck normal hook trust and the exact command, all source hashes, included allowance, private trace/checkpoint storage and configuration. Do not change trust automatically, copy credentials, install a runtime or modify global settings. Confirm the session is ephemeral and pathless with expected instruction sources and effective tool restrictions before inference. No integration initialization or unexpected enabled hook is acceptable. A changed candidate requires affected review and checks again.

Only the exact fictional checkpoint reader may execute as a model tool. Its client handler must validate the session, continuation turn and arguments, allow one read after the observed reminder, and return only that session's fictional checkpoint as untrusted evidence. The harness's narrowly specified metadata, checkpoint fixture save/read, manual compaction and cleanup operations are separate control-plane actions; enumerate and review them too. An allowlist exception is a different protocol, requiring independent review and evidence of safe containment before any run; it cannot rehabilitate the invalid run.

Preserve 18:00, `owner/02`, the reason that both operators can review after work, the mailing-address approval hold, the unrun integration check and a local-only next action. Request the continuation, then require the matching reminder to complete before model output and before the single permitted read. Do not explicitly instruct retrieval in that continuation; record the remaining cues from the tool description, requested fields and reminder. Require the completed answer. Preserve the complete bounded event/request trace, tool attempts, configuration assertions, process exit and cleanup outcome.

Record final allowance and scoped persistence checks even when semantic screening fails, if safe and available. On an isolation breach, stop the owned process immediately; perform only separately safe metadata reconciliation after it has exited. Never resume an invalid run to obtain a nicer answer. Missing final checks stay unobserved. A missing exact session in current/archived listings does not prove no transient persistence or other storage.

Report four separate results: **execution validity**, **transport/lifecycle**, **mechanical factual screen**, and **independent semantic review**. Mechanical checks require the exact hidden marker/revision and canonical factual categories, while allowing prose paraphrases. A distinct reviewer checks the full answer for accurate reasons, holds, uncertainty, unsupported claims and contradictions. Correct categories paired with prose authorizing a send must fail semantic review. Wrong/stale markers, missing holds, fabricated checks, duplicate reads and forbidden tool attempts have prospective negative cases. An overall pass requires every required gate; pending review or missing evidence is not a pass.

Even a valid pass establishes only this bounded fictional manual-compaction behavior. It does not establish automatic checkpoint writing, loss of the facts during compaction, reminder causation, automatic compaction, ordinary desktop recovery, safe replay of real effects, successor-chat creation or general reliability.

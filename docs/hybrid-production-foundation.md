# Production foundation decision and migration contract

October 27, 2026. Stage 2 design, following the fictional same-workspace email proof at `fa9c3fa`. This document selects the next engineering experiment; it does not activate a database, identity service, migration or production workflow. [Tasks](../TASKS.md) owns current status; [hybrid implementation](../pipeline/HYBRID-IMPLEMENTATION.md) retains proof history.

## Decision

Retain the current conditional store for the bounded fictional proof. Assess managed PostgreSQL for production records and retain private immutable files behind the existing authorized application routes. Do not build competing provider adapters or put the whole workspace into SQL and call scaling complete.

Netlify Database remains the first host-compatible candidate, but current public billing prevents treating it as a proven fit for the existing budget. Its documented rate is 10 credits per compute-unit hour. An illustrative eight awake hours on 22 workdays at the minimum unit uses 1,760 credits before other services; the last verified account allowance was 1,000 credits shared with other sites. This is a scenario, not a measured bill. The documentation still contains an expired July storage promotion without a definite current storage rate. [Billing](https://docs.netlify.com/build/data-and-storage/netlify-database/billing-and-usage/)

Personal automatically scales from one to four units; only higher plans can customize that range. Frequent reads can prevent the five-minute idle sleep. Therefore, replacing each existing 15-second desk refresh with a SQL read is not an acceptable unmeasured migration. Caching may reduce display reads, but must never supply authority for approval or dispatch. [Scaling](https://docs.netlify.com/build/data-and-storage/netlify-database/configure-auto-scale/), [sleep](https://docs.netlify.com/build/data-and-storage/netlify-database/configure-sleep-on-inactivity/)

Provider selection remains conditional on current account terms, included-credit headroom, identity assurance and measured restore/cost behavior. Read-only account inspection may proceed through existing authorized access. New service setup, credentials, grants, paid capacity and production activation retain their separate authorization requirements.

One credible budget alternative is Supabase Free for PostgreSQL and Auth only, keeping files in existing Netlify Blobs. Its 1 GB Supabase file quota would not apply to that split. Its 500 MB database and published egress limits, possible pause after a week of inactivity, and self-managed free-tier backups still need a measured pilot and recovery procedure. It is a candidate for a bounded pilot, not a claim of full unattended availability. Do not manufacture activity to bypass inactivity rules. Paid plans are outside the existing additional-spend budget. [Pricing](https://supabase.com/pricing), [backup limitations](https://supabase.com/docs/guides/platform/backups)

## Preserve the existing boundary

`ConditionalLifecycleStore` currently reads, validates and conditionally writes the complete workspace, capped at 20,000,000 serialized bytes. Its callback runs once; conflicts do not replay external effects. Typed validation independently reconstructs permitted changes before publication. Preserve those properties and the existing stable event IDs, uncertainty states and exact content/PDF/MIME evidence. [Current store](../pipeline/lifecycle-store.mjs)

The current workspace is the only aggregate whose complete dependency set is demonstrated. Reducers and validators also inspect shared policy, budgets, events, actions, writing styles and asset indexes. A project-only SQL write cannot safely replace that transaction until those dependencies have explicit versions and a complete read/write set. Keep correct business-rule code; change its persistence boundary deliberately, without permanent double-writing.

Existing `hash()` values derive from `JSON.stringify`. JSONB can reorder object keys; reserializing historical evidence would change fingerprints. Preserve original serialized text/bytes and hashes for historical approvals, intents and receipts. Relational columns or JSONB may serve as query projections, with identity/version checks back to that evidence. Any future canonical representation requires an explicit schema version; it must not silently rewrite old authority. [Hash and reducers](../pipeline/lifecycle.mjs)

## Transaction and worker contract

For each selected command, record authenticated actor, workspace/project, stable event ID and fingerprint, expected record revisions, policy/assignment/restriction versions, referenced source/file hashes, and any existing intent or uncertainty. A matching retry returns its retained receipt; the same ID with different meaning is rejected.

One short database transaction must validate the complete current read set and atomically persist the business transition, event receipt, usage reservation and pending external intent. Existing `actions` and `operations.requests` are the outbox: normalize their representation rather than adding a second queue. Use parameterized queries on one checked-out connection. Lock ordering and conditional revisions must be explicit. The documented Netlify pool supports transactions; actual selected-driver behavior remains a test gate. [Pool API](https://docs.netlify.com/build/data-and-storage/netlify-database/api/)

No model, email, payment, file transfer or deployment call runs inside a transaction or automatic transaction retry. A worker claim binds its lease generation, membership/authentication generation, policy, recovery epoch and runtime/schema versions. Recheck these and current pause/source/approval conditions after awaited work before granting a new effect or publication. A stale worker cannot overwrite a successor. Expired leases do not authorize resending an uncertain action. Preserve original-effect evidence and reconciliation even after revocation or pause; stopping new authority must not erase an outcome already in flight.

PostgreSQL isolation does not remove application race handling. Treat serialization failure as a conflict; never automatically rerun `change(fn)`, domain reducers, original/grant reads or generation of claims/deadlines. Any future retry of fixed SQL needs its own proof that it preserves the frozen transition and all preconditions. Unknown COMMIT requires exact retained-receipt readback, not blind resubmission. `SKIP LOCKED` can help claim queue rows but is unsuitable as a general consistent record read. [Isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [locking](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

## Operator identity and private files

Replace static proof keys only through a separately verified identity integration. Map two approved provider subjects to server-owned EVZ operator IDs; do not infer roles from a shared sending address or accept client-supplied role claims. Retain individual attribution and existing CSRF/session protections. Check current membership/revocation and authentication generation at sensitive mutations. Role changes and revocation must invalidate authority even if an old provider token is still cryptographically valid. Worker tokens remain task-scoped and never become operator sessions.

Keep historical role-key events unchanged; do not retrospectively attribute them to an unverified person. New verified-principal evidence belongs in a co-committed audit record or an explicitly versioned future event. Provider Gmail/Drive/Calendar grants remain separate from operator login, with their existing workspace/deployment/policy encryption bindings. A database migration grants no permission to copy or expand them; inspect valid reuse/rebind requirements before requesting new grants.

Netlify reversed its Identity deprecation; it is a candidate, not an assumed MFA implementation. Verify actual operator enrollment, required assurance and recovery. Dashboard MFA alone does not establish MFA for desk sessions. Keep application audit records independently of provider audit-plan features. [Identity status](https://www.netlify.com/blog/auth0-extension-identity-changes/), [Identity documentation](https://docs.netlify.com/manage/security/secure-access-to-sites/identity/overview/)

Keep file bytes outside business rows, addressed by workspace/project, immutable version, hash and size. Upload to an unpublished immutable key, verify bytes, then transactionally publish its metadata/reference. A failed transaction leaves an unreferenced object, not a usable client attachment. Do not automatically delete retained originals or uncertain evidence. Reads authorize the exact project/version before returning bytes; no generic arbitrary-key endpoint. Database previews must not copy real client data into an accessible test environment. Existing site-wide Blobs namespaces also require explicit preview isolation. [Blobs](https://docs.netlify.com/build/data-and-storage/netlify-blobs/#sensitive-data)

## Migration and recovery

1. Freeze source writes and new dispatch; inventory and reconcile in-flight effects. Record source revision, schema, binding and complete file manifest. Unknown outcomes remain liabilities.
2. Export exact evidence and immutable file bytes, including unfinished-attempt dispositions. Verify hashes, counts, relationships and total sizes before any destination publication. Production data is outside current authorization.
3. Import into a separate disabled target with a new recovery/authentication generation. Preserve history and uncertain intent identities; revoke unfinished worker/session authority and require fresh target-bound content/send approvals. Do not carry secrets or active grants in the export.
4. Exercise both operator sessions, restart, missing/corrupt file rejection, wrong-project access, stale revisions, concurrent updates and complete combined restore. Record actual recovery time and loss window before making promises.
5. Cut over one authoritative writer only after acceptance. Retain the old system read-only for recovery. Even before external effects, target human writes require verified reverse export/reconciliation and a fresh epoch before returning to the old target. After external claims/effects, rolling back application code or a database snapshot is insufficient: retain and reconcile their ledgers, reservations and receipts as well as later records before enabling replacement work.

Netlify documents daily and publish-time database snapshots with plan-specific retention; these are not a coordinated backup of private object bytes or proof of arbitrary-time recovery. Bind the exact database snapshot/cut identifier to the immutable object-manifest hash and verify every required original. Retain existing incomplete-attempt recovery holds; publish the destination manifest last, only after record and file verification. [Database recovery](https://docs.netlify.com/build/data-and-storage/netlify-database/backup-and-recovery/)

## Local email dependency contract

The authorized local successor uses `email-dependency-contract.mjs` beside the existing typed witnesses at `ConditionalLifecycleStore.change`. It covers the fictional task/review profiles and the paired declared-thread task/mail profile: create/result/adopt, signed reply records including stop/handoff, and exact approval/reserve/materialize/dispatch/sent/read/verified/hold. Other capabilities keep their existing validators. No caller field, persisted schema, endpoint, credential, dependency, adapter or queue was added.

The version-1 descriptor binds the untouched pre-state's ETag, revision and exact envelope hash; the actual capability binding; and the typed witness's command, actor, project, identity, time/deadline and hash. It declares conservative read groups for policy/recovery, source/ownership/restriction, incoming and unsettled-send predicates, event identity/order, styles/catalogue and task identity/capacity. Mail adds combined sender reservations and legacy approvals. Canonical record transitions declare global notification sources and operation-cycle dependencies.

The complete envelope remains an explicit read dependency. These groups describe current coupling; they are not a complete independently versioned per-client read set or a trace of every executed property access. A future scoped implementation cannot remove that dependency on the strength of these checks.

Permitted write paths are command-specific: exact task/current pointer/replaced task; selected project plus exact signed event for adoption/review; existing selected-project actions for stop/handoff and the exact deterministic information-task/sequence-stop IDs where required; global notification preparation and cycle invalidation where the reducer requires them; or exact mail action/intent/email record and separate approval event. Missing/altered descriptor fields, widened write declarations and writes outside those paths fail closed. The independently reconstructed transition still verifies exact values within permitted subtrees; a permitted path alone does not authorize an edit.

Mail callers finish their existing witness inside their callback, so the store constructs the internal companion afterward from the retained untouched pre-state. Descriptor validation runs BEFORE independent replay: original rereads and live expiry/deadline checks remain the final publication checks. The callback still runs once and the unchanged ETag still arbitrates publication races. The descriptor is neither stored nor accepted from an HTTP caller; it contains hashes and paths, not bearer credentials or client content.

Focused verification: `node --test email-dependency-contract.test.mjs shared-email-draft-tasks.test.mjs shared-email-draft-review.test.mjs shared-email-draft-dispatch.test.mjs`. The new tests cover incomplete/widened contracts, unrelated writes, changed collections/source predicates, task-versus-review permissions and a differential adoption with another client's notification preparation/resolution and cycle-cache invalidation. Existing signed tests retain stale-source, stop/handoff, replacement/late-result, expiry/deadline, exact historical evidence, duplicate/ACK loss and full MIME/receipt checks. Aggregate commands remain `npm run check` and `node --test --test-concurrency=1` from `pipeline`. Task/checkpoint status owns final run results; no rollout follows from a local pass.

## Native compatibility evidence and next acceptance

The private native PostgreSQL 17.9/pg 8.23.1 experiment completed after separate local setup authorization. Ten transaction/journey checks and one controlled-restart check passed, including real conflicts, rollback, discarded acknowledgement after COMMIT, exact text/hash preservation, and the existing signed task-to-injected-MIME-receipt journey. Its technical write receipts are not a newly implemented domain outbox. The stopped test cluster and pending cleanup are recorded in the private checkpoint; Docker was not repaired or restarted. No application database dependency was installed.

That whole-workspace text-plus-revision transaction remains a temporary compatibility baseline. It retains the 20 MB serialization, whole-state replay, contention and recovery-size limits. The local descriptor above makes those dependencies explicit without claiming to remove them. The next partitioning decision must address global notification/cycle writes and historical revision/order dependencies before introducing independent client transactions. Do not turn the private fixture into a permanent disabled adapter.

Reuse existing behavioral fixtures for duplicate/lost acknowledgement, same-event/different-actor rejection, stale review, assignment/stop, original corruption, uncertain send and disabled recovery. Add only SQL-specific cases: concurrent connections, commit-acknowledgement loss, rollback, database restart, serialization conflict, lease fencing and historical hash round-trip. Use a small deterministic workload to measure rows/bytes read and written, latency and lock contention; local timing does not prove hosted credit consumption.

Stage 2 remains open until independent sessions/restarts, identity revocation, combined restore, bounded load and actual provider cost fit the selected operating scope. A deliberately limited pilot is allowed only with measured limits and explicit remaining gaps; it does not establish long-term scale, retained-audio capacity or unattended production readiness.

## CI, release and rollback

Git pull requests own content and code changes. The `site-check` workflow runs syntax, build, static route/asset checks and inquiry tests on every pull request and change to `main`. GitHub `main` protection requires an up-to-date passing `site-checks` result and a pull request; it applies to administrators, requires linear history and resolved conversations, and disallows force pushes and deletion. Netlify's GitHub App is restricted to this repository. Netlify builds from `main`; production is public while previews stay private. [PR #50](https://github.com/Vziraka/ensizziyo-web-studio/pull/50) passed review and checks, merged at `c131ea3`, and produced [this successful deploy](https://app.netlify.com/projects/evz-digital-studio/deploys/6ad2b3c157ba5073205eaf5c). The owner then approved the visibility change. The live custom domain, `www` redirect, HTTPS, public routes, `noindex`, private preview and form receipt were verified. For rollback, return production visibility to Private immediately if visitor access or form handling fails; restore the [prior production deploy](https://app.netlify.com/projects/evz-digital-studio/deploys/6ad27f92bb1c8bbb55468f7f) or revert the Git change if the published revision is faulty, then recheck the form and public URLs.

This is practical CI/CD and Git-managed deployment configuration. A Kubernetes platform, cluster controller or formal GitOps reconciliation loop would add operational work without a current need for this static site. The [OpenGitOps principles](https://opengitops.dev/) describe a stricter model with declarative desired state and automatic reconciliation; this site can adopt more of it if its infrastructure grows.

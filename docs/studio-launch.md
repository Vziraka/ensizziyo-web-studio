## Inquiry and data ownership

The studio form asks for description, name and email; business, website and sample context are optional. The visitor reviews the details, then `sendInquiry` posts URL-encoded data to the `studio-inquiry` Netlify form. Client validation bounds fields; a non-OK response or network error keeps the entered details and shows retry. Local form state stays in memory. Eight demonstration forms and actions remain simulated and visibly labelled.

Form detection is enabled. A rebuild found one active `studio-inquiry` form, and the private inquiry page showed required-field errors before accepting a synthetic submission. The completion page appeared and Netlify's **Verified submissions** list stored the same synthetic fields. Configure verified-submission email notifications to the selected `hello@evzdigital.studio` owner-controlled business inbox once it exists. A submission response and provider record do not prove email delivery; verify the notification in the inbox with another synthetic inquiry before launch. [Netlify's form notification documentation](https://docs.netlify.com/manage/forms/notifications/) describes that setup. One Google Workspace Business Starter user on flexible billing is the mailbox choice, matching the separate business-system account plan; Google's signup pricing page displayed **$8.40 per user per month** on its flexible setting. The address and account are not active yet.

After the lifecycle system's inbound record owner, consent fields, status, deduplication key and failure handling are defined and verified, connect it from verified Netlify submissions. The business inbox is the first operational destination, not a dependency on completing outbound automation. Keep API keys and mailbox settings in provider environment configuration only.

## CI, release and rollback

Git pull requests own content and code changes. The `site-check` workflow runs syntax, build, static route/asset checks and inquiry tests on every pull request and change to `main`. GitHub `main` protection requires an up-to-date passing `site-checks` result and a pull request; it applies to administrators, requires linear history and resolved conversations, and disallows force pushes and deletion. Netlify's GitHub App is restricted to this repository. Netlify builds from `main`, and the project stays private until all release checks pass. Verify a private PR deploy preview during the next reviewed change. Promote the reviewed build to public only after release approval, connect DNS and HTTPS, and verify the live URL. Retain [the current successful deploy permalink](https://app.netlify.com/projects/evz-digital-studio/deploys/6ad27f92bb1c8bbb55468f7f) and use Netlify's prior-deploy restore or a Git revert for rollback.

This is practical CI/CD and Git-managed deployment configuration. A Kubernetes platform, cluster controller or formal GitOps reconciliation loop would add operational work without a current need for this static site. The [OpenGitOps principles](https://opengitops.dev/) describe a stricter model with declarative desired state and automatic reconciliation; this site can adopt more of it if its infrastructure grows.

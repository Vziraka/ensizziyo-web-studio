Current [credit-plan documentation](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/) lists Free at $0 with 300 credits per month; [bandwidth consumes 20 credits per GB](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/). ### Inquiry retention routine to activate before launch

The owner is responsible for this manual routine until the separate inbound lead path has its own verified retention process. Keep the working register in an owner-only business workspace, **outside Git**. For each real inquiry, record only the Netlify submission identifier, contact email, date of the last inquiry-related contact, whether a project started, and the deletion due date. Update the last-contact date after each reply. Do not put message text, exports, or customer identifiers in a repository, issue, PR, or public calendar reminder.

On the first business day of each month, review inquiries whose deletion deadline falls before the *next* monthly review. If no project started and there is no documented reason to retain one, remove it before its 12-month deadline: select the matching record in Netlify's `studio-inquiry` verified or spam submissions and use **Delete submission**; find the matching notification and conversation in the business mailbox, including sent replies, move them to Trash and use **Delete forever** for those messages. Gmail's ordinary Delete leaves a message in Trash for up to 30 more days, so Trash alone does not satisfy this promise. Recheck the two services, remove the personal fields from the working register, and keep only an anonymous completion date/count in the private operating log. If a project started or a legal obligation affects retention, record the exception privately and use the applicable project terms or obligation instead of silently resetting the inquiry clock. Handle a verified deletion request through the same two-service check promptly rather than waiting for the monthly review. [Netlify's deletion steps](https://docs.netlify.com/manage/forms/submissions/#delete-a-form-submission) and [Gmail's Delete forever steps](https://support.google.com/mail/answer/7401) are the provider instructions.

Before making the form public, create the private register and monthly owner reminder, then rehearse the two-service deletion with synthetic records. A written procedure alone is not proof that the retention promise is operational.

## CI, release and rollback

Git pull requests own content and code changes. The `site-check` workflow runs syntax, build, static route/asset checks and inquiry tests on every pull request and change to `main`. GitHub `main` protection requires an up-to-date passing `site-checks` result and a pull request; it applies to administrators, requires linear history and resolved conversations, and disallows force pushes and deletion. Netlify's GitHub App is restricted to this repository. Netlify builds from `main`, and the project stays private until all release checks pass. [PR #41's Deploy Preview](https://app.netlify.com/projects/evz-digital-studio/deploys/6ad2808b0e2686c05d025974) built successfully, opened for the authenticated owner and showed **Private**. Promote the reviewed build to public only after release approval, connect DNS and HTTPS, and verify the live URL. Retain [a known successful prior production deploy permalink](https://app.netlify.com/projects/evz-digital-studio/deploys/6ad27f92bb1c8bbb55468f7f) and use Netlify's prior-deploy restore or a Git revert for rollback.

This is practical CI/CD and Git-managed deployment configuration. A Kubernetes platform, cluster controller or formal GitOps reconciliation loop would add operational work without a current need for this static site. The [OpenGitOps principles](https://opengitops.dev/) describe a stricter model with declarative desired state and automatic reconciliation; this site can adopt more of it if its infrastructure grows.

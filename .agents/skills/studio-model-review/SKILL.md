name: studio-model-review
description: Check model releases and account/tool availability before substantial EVZ work and during the weekly model review. Recommend evaluated changes without changing model defaults, routes or budgets automatically.
---

Read docs/model-review.md and the newest recorded review. Use official provider release/model documentation for the providers already used by the studio. Research announcement dates, retirements and changes relevant to the actual task. Reuse this week's release research before substantial work, but freshly check the intended execution surface/account when available. Do not rely on training knowledge, model names in old docs, or the desktop picker to establish CLI/API access.

Inspect available metadata-only model/usage tools or the installed CLI's documented catalog. Never extract tokens/cookies, print credentials or start inference merely to list models. Distinguish provider, agent application, exact model, reasoning setting, account access, tools, quota and billing. If availability cannot be established, label it unknown and retain the current working route; check another already-approved route only within its authorization.

Record the check date, source URLs, relevant change, observed availability (or unknown), current selection, recommendation and evaluation status in docs/model-review.md. Only public facts belong in Git. Account identifiers, balances and raw tool reports stay in an authorized private evidence directory. Avoid unchanged-status rewrites and duplicate notifications.

A release is a candidate for evaluation, not authority to switch. Recommend representative tasks and compare quality, speed, cost/allowance and failures. A real evaluation consumes allowance and requires an existing bounded authorization; never buy credits, enable overage, install CLIs or invoke a paid API to complete this review. Never change defaults, model routing, scheduled-task models, reasoning settings or reservations automatically. Do not pause unrelated implementation merely because a release is untested.

Weekly runs remain quiet unless there is a relevant new release/retirement, an access failure, or a decision the owner needs to make. Preserve the last usable baseline on source/metadata failure. Report a material failure once with the source and recovery step; do not invent an up-to-date check.

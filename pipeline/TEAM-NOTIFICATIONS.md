# Internal alerts and weekday team summary

The separately disabled [shared standing dispatcher](SHARED-INTERNAL-DISPATCH.md) composes these same source templates with registered incoming and a distinct finite owner policy. Existing preparation and each-message approval below keep their original gates.

Verified attention events prepare private messages in **Needs attention → Owner alerts and team summary**. Replies go to the assigned operator, or the owner when unassigned. A verified reply includes meeting requests for human review in the original mailbox; the desk does not guess meeting intent from private text. Calendar records needing review, uncertain provider actions, urgent support and saved problems also prepare attention messages. Global problems go to the owner. Private reply bodies, call notes and raw error details are not copied into notification text.

The same active source does not prepare repeatedly. Handoff resolves the old audience's unsent message and prepares one for the new responsible operator. Reviewing/resolving the source marks its pending message resolved before delivery. A later occurrence can prepare again. None of these states means a message was sent.

At or after **9am America/New_York on weekdays**, clock preparation saves one summary for each of the owner and friend roles. The digest records its due time, actual preparation time and lateness. Before 9am and on weekends it prepares no digest; it does not backfill missed weekend/previous-day summaries. The daily snapshot stays immutable through retries/restarts. Counts distinguish new prepared businesses, due callbacks, other due call tasks, interested projects and attention items; simulated calls never become actual contacts.

## Actual callers

- Lifecycle events prepare current attention messages in the same state transaction, without external effects.
- The existing local `service` host checks preparation every 60 seconds while it is awake. This does not establish a computer-off scheduler.
- Local and hosted authenticated `GET /api/team-notifications` returns the private preparation view. CSRF-protected `POST /api/team-notifications/prepare` checks current attention and digest time; the hosted prefix is `/desk`. The UI's **Check due alerts and team summary** calls that route.
- `node lifecycle-cli.mjs notifications` reads prepared messages; `node lifecycle-cli.mjs prepare-notifications` performs the clock check against the configured private state directory.

The source history is bounded to 500 messages and the UI returns the latest 40. A full history holds further preparation with a visible reason; it cannot discard the incoming verified reply. Retention/archive behavior must be reviewed before production use. Preparation creates no send action or provider intent. The separately disabled exact caller below requires explicit policy and message authorization.

## Disabled exact internal delivery caller

It adds no queue, scheduler, automatic approval or production capability. The default preview, preparation clock and account connection send nothing. The signed same-origin/CSRF caller is `POST /desk/api/exact-team-notifications/policy|authorize-policy|package|approve|dispatch|reconcile`. [The disabled example](exact-team-notifications.example.json) contains only `.invalid` placeholder addresses, including a deliberately unusable sender. It is review material, not a valid binding or approval. An explicitly selected future owner grant/account and the existing accepted business sender must match before even the fictional candidate can be authorized. No tokens belong in this configuration.

Authorization has two distinct steps:

1. `policy` returns the exact configuration and hash. Only a signed owner can call `authorize-policy` with current `revision`, fresh `event_id`, `policy_sha256` and `authorized:true`. This records a policy event in existing lifecycle state; configuration alone is not authorization.
2. `package` takes an existing `notification_id`. It derives the complete envelope from saved source, role and policy; browser recipient/body fields cannot alter it. The saved recipient role alone may call `approve` with current revision, fresh event ID, exact `package_sha256`, `approved:true` and `facts_checked:true`. This creates the ordinary exact-mail action. `approval_mode:'each-message'` is mandatory: the owner policy does not approve messages or authorize recurring sends. `dispatch` is a separate explicit call with the saved action ID. Each daily recipient approves their own digest. No standing automatic delivery authority is inferred from the user's alert requirement.

The package fingerprint binds exact From/To/subject/full body/signature, role, prepared source ID/hash/due time and entire policy/configuration revision. Before reservation and again after awaited sender preflight, current strong state must retain the source, role and approved envelope. Resolved/changed/reassigned attention holds even without another preparation tick. Digests retain their immutable daily snapshot, become eligible at weekday 9am Eastern across DST, and hold after their original Eastern date; old summaries are never backfilled. A changed envelope cannot replace an already approved/reserved action. Reconciliation uses its saved original MIME only.

`dispatchExactMail` reserves the existing `${action.id}-intent` before token/HTTP access, retains the exact MIME and marks the claim **Uncertain before POST**. Reservation time and its Eastern budget date are captured together inside the state mutation; crossing an Eastern date during preflight holds before release. Internal daily limits (1–20) and total policy limits (1–100) are separate from prospect allowances. Every internal reservation also counts against the unchanged combined 20/day sender ceiling, including native/information/exact reservations and uncertain attempts. This never increases the existing prospect allowance or 25-new-business target. Concurrent requests use the existing conditional state authority; no HTTP runs in a CAS callback.

The same Gmail preflight checks the exact owner account and accepted sender; the existing composer/send/raw Sent verifier checks complete routing/content headers, date, Message-ID, full decoded body and signature. This verifies sender-side Sent state, not recipient inbox delivery. Loss/timeout after claim, duplicate invocation, empty/ambiguous Sent search, unsupported rewrite or mismatched readback retains **Uncertain**, with no retry/resend permission. The deterministic Message-ID is reconciliation only. Internal delivery failures do not recursively create another internal alert. Existing Needs attention cards show retained intent/receipt status, including explicit inbox-delivery uncertainty; checking preparation never sends.

Recovery uses the existing complete lifecycle backup: actions, policy events, immutable MIME, reservations and uncertainty survive; credentials and executable configuration do not. Restore stays disabled and requires an explicit trusted rebind before provider reconciliation. Removing the new flag holds dispatch; preserve old intents when rolling code back, and never route them through a legacy sender.

## Disabled hosted clock candidate

`notification-clock.mjs` opens only an **existing fictional, execution-disabled** workspace through the same strong-read/CAS store and `prepareTeamNotifications`. It never initializes a workspace, dispatches notifications, reads provider credentials, imports records, resumes research, invokes models or executes email actions. Lifecycle events already prepare important alerts in the mutation transaction; the clock supplies passage-of-time checks for digests and ageing uncertain operations. Each message retains its immutable recipient role; handoff resolves the unsent old message before preparing the new role. A role snapshot is not a verified external delivery address.

The existing `node scripts/build-desk-assets.mjs` build step also generates ignored `pipeline/netlify-functions/notification-clock.mjs`. **Default builds, including production and Deploy Previews, emit only a 503 held response with no imports and no schedule declaration.** Neither `netlify.toml` nor hosting configuration enables a schedule. A future separately authorized fictional schedule requires all these gates together; none was configured in this increment:

- Build `CONTEXT=production` plus exact `EVZ_NOTIFICATION_CLOCK_BUILD=scheduled-fictional-preparation-only` emits literal `schedule:'* * * * *'`.
- Runtime `EVZ_NOTIFICATION_CLOCK_ENABLED=fictional-preparation-only`, an explicit `EVZ_NOTIFICATION_CLOCK_SITE_ID` matching trusted `context.site.id`, and Netlify's `DEPLOY_ID` matching trusted `context.deploy.id` are required before storage access. Trusted context must be production and `published` true; client headers/body cannot supply these values.
- `EVZ_OPERATIONS_BLOB_NAMESPACE` must name an existing `evz-redesign-proof-…` fictional store with the preview seed marker. Existing validation requires research, outreach, connector writes and transcript AI off, all records fictional, and the complete envelope within the unchanged **2 MB** proof limit. No canonical production state can be loaded.
- A fresh included-credit review, explicit finite trial duration and stop/readback plan, and approval for any production-scoped fictional configuration remain necessary. Removing the build flag and rebuilding removes the schedule; removing the runtime flag holds preparation before storage. No new service, dependency, account, charge or allowance was added.

[Netlify's scheduled-function contract](https://docs.netlify.com/build/functions/scheduled-functions/) supports all plans, uses UTC, permits no public URL invocation, and runs schedules only for published deploys. Preview **Run now** and local invocation prove manual handler behavior only. The [30-second execution limit](https://docs.netlify.com/build/functions/configuration/) bounds each invocation. A minute cadence lets the existing `America/New_York` rule select weekday 9am across both DST offsets; it is an intended check cadence, not an exact delivery guarantee. Delayed ticks prepare today's snapshot once with actual lateness; missed prior days are not backfilled. Important events prepare immediately when committed; external delivery latency remains unproved and delivery disabled.

Each eligible tick reads bounded state at most three times and attempts at most one conditional write; unchanged state causes no write. There is no retry loop or secondary queue. Concurrent ticks fail safely with a conflict. An uncertain write returns a hold; the next tick strongly reads saved IDs/fingerprints before preparing again. Existing actions/approvals and private notes/transcripts are untouched. The 500-message history hold remains. Minute invocations and Blobs reads use shared hosting credits even without writes; plan availability does not establish unlimited free execution or current credit headroom.

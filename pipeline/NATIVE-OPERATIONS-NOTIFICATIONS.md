# Native operations notifications

This source is default disabled. It prepares a narrowly scoped ChatGPT MCP Events transport for the existing saved operations incidents and the daily 18:00 America/New_York summary. It does not establish a live connection, schedule, callback receipt, ChatGPT task, device notification, second-operator access, or PC-off operation. No model API, Gmail operation, paid usage or automatic overage is added. The existing commercial-mailing-address hold and provider-intake gates remain unchanged.

## Saved status without native subscriptions

The separate explicit `saved-operations-status-v1` gateway mode reads saved operations status without opting the canonical workspace into native notification policy, subscriptions, callbacks or credential storage. Existing `mcp-events-v1` behavior stays unchanged. The same `/desk-notifications/mcp` entry is POST-only in this mode and exposes exactly the read-only `evz_notifications_status` tool with strict empty input `{}`; it advertises no Events capability or handlers. It is source preparation only: no clock, connection, credential provisioning, deployment or hosted task is enabled. A missing mailing address does not gate this status, manual desk work or separately approved noncommercial acceptance; commercial activation retains its separate hold.

Set the reviewed server-only `EVZ_NATIVE_NOTIFICATION_GATEWAY` to this mode, `EVZ_NATIVE_NOTIFICATION_GATEWAY_POLICY` to the closed policy in [the expired fictional example](saved-operations-status.example.json), `EVZ_NATIVE_NOTIFICATION_SOURCE_BINDING` to the exact canonical production `shared-operations-desk-v1` binding, and `EVZ_NATIVE_NOTIFICATION_SOURCE_BLOBS_TOKEN` to the separately authorized source-site token. Gateway site/deploy/context/published/origin are exact trusted metadata and the gateway site must differ from the source. Binding and full canonical configuration hashes must match policy and the existing manifest. There is no permanent state/revision/envelope pin: a later legitimate snapshot under the same B/config is accepted. Configuration or binding changes need newly reviewed explicit configuration.

The policy has exactly `schema_version,mode,site_id,deploy_id,context,published,origin,source_access,source_binding_sha256,source_config_sha256,owner_credential_sha256,friend_credential_sha256,excluded_credential_sha256,starts_at,expires_at`. Version1 uses `source_access: cross-site-token-v1`. Canonical UTC access starts no later than the request and expires after it, with a maximum policy duration of seven days; this ceiling is not a seven-day trial or quota attestation. Owner/Friend bearer values are distinct lowercase64-hex credentials. Their policy digests follow the existing `hash(string)` convention: **SHA-256 of the raw UTF-8 bearer string**, without JSON quotes or hex decoding. Excluded worker/discovery credentials form a unique2–16-entry digest list, distinct from both roles; the server source token must differ from every role/excluded credential. No raw bearer or source token belongs in source, a Page or a task prompt. The source token may have broader provider access than this application; namespace least privilege is not established.

Gateway identity/window and bearer role are checked before source access. Initialize/discovery perform zero source reads. A status call performs at most two strong JSON reads of only the bound `workspace` key: project one typed snapshot, then fence the same ETag/full envelope immediately before return. The final fence follows awaited SDK serialization/cleanup. Source/policy/token/context/window/deadline are checked around awaits and every default SDK transport hop. The default transport permits only the exact source lookup GET and its issued HTTPS S3 storage GET, with no redirects or credential forwarding to storage, bounded bodies and the remaining invocation deadline. Normal status therefore uses two envelope reads/four authorized storage HTTP requests; initialization/list uses none. Storage GETs are the deliberately allowed provider boundary, not zero network activity. No other provider or storage operation is available. A race/expiry/unavailable source returns fixed unavailable text, never an empty healthy result or an automatic retry. Whole requests are bounded to25seconds, request bodies16KiB and responses64KiB; a real large envelope may exceed useful latency/cost limits even within those caps.

Successful structured output is closed: `schema_version,items,summary,freshness,holds,truncated,fingerprint`. Each of at most40 items contains only role-salted SHA-256 `id`, closed `kind` and `state`; recipient filtering precedes selection. Active saved records take precedence, then recent retained history; returned items are sorted by opaque ID. Actual saved digests are `saved`, linked stored resolutions are `resolved`, and unlinked/malformed retained history is `held`. Unsaved live incidents appear only as a hold/truncation indicator: polling creates no incident, resolution, digest or18:00 event. Kinds are connection/intake/delivery/research/callback/reply/meeting/support/operation/daily_summary. Summary is only the existing closed nonnegative `nativeSummary` counts/day/generated time: these are **workspace aggregates**, not role totals; underlying ID arrays are absent.

Freshness contains check time, source update/revision and saved health observation/state. Health is current only when its saved canonical observation age is0–15minutes inclusive; future/malformed/absent evidence is unknown and older evidence is stale. This is not a live Google probe. Holds are sorted closed codes only (`health_unknown`, `health_stale`, `unsaved_incidents`, `notification_capacity`, `unlinked_saved_history`); no raw stored hold/error text is returned. Truncation discloses omitted role-matching or unlinked/unsaved evidence. The role-specific fingerprint covers selected IDs/kinds/states, aggregate count values/day, holds/truncation and health category; generated/check/observation timestamps, freshness countdown and unrelated revision/note changes are excluded. Names, contacts, content, raw source/project/notification IDs, callbacks, credentials and provider/cause diagnostics never enter the response.

## Preparation and authority

An explicitly prepared `shared-operations-desk-v1` manual binding may include `nativeNotifications` using the closed policy in [the placeholder](native-notifications.example.json). Its site, deploy and origin must match the binding. The policy is finite, at most seven days, and caps daily/total attempts with a 30% reserve. Existing manifests and old profiles cannot acquire this policy by setting an environment variable. Imported native history must already be paused, without active subscriptions, allowance or live claims. Restoring a portable backup revokes subscriptions, clears allowance, increments the epoch and turns claimed attempts uncertain; ciphertext and master keys are never included. A changed reviewed policy requires a signed owner `rebind` with the exact old policy hash and explicit authorization before any new allowance or subscription.

The signed same-origin desk caller requires `EVZ_NATIVE_NOTIFICATION_ADMIN=mcp-events-v1` and an opted-in policy: `POST /desk/api/native-notifications/allowance`, `/pause`, or `/rebind`. Only the owner may use these controls. `allowance` takes the current revision, actual `observed_at`, `expires_at`, `remaining_percent`, `included_only:true`, and a nonsecret `evidence_ref`; the observation expires within 15 minutes and must be above 30%. This is an attestation of separately observed included usage, not an automated quota reader. `pause` accepts the revision and a Boolean; `rebind` accepts revision, `previous_policy_sha256`, and `authorized:true`. Do not put credentials, balances or client data in the evidence reference. A new workspace starts paused; no configuration flag substitutes for these signed transitions.

The default-disabled `/desk-notifications/mcp` function requires `EVZ_NATIVE_NOTIFICATION_GATEWAY=mcp-events-v1`, an exact closed gateway policy, and exact trusted gateway site/deploy/context/published/origin. Role credentials are distinct 64-hex bearer values whose raw-string SHA-256 hashes are in the reviewed policy and differ from the two supplied existing discovery-role hashes. Authentication precedes storage access. The source must carry the exact opted-in policy and remain within its finite policy window.

The original same-site mode binds gateway and canonical site, deploy and origin together and uses the trusted function-context Blobs mechanism. A separately reviewed cross-site mode is explicitly enabled by the two additional policy fields `source_access: "cross-site-token-v1"` and `source_binding_sha256`, the hash of the entire exact canonical manual binding. It requires a distinct gateway site and the server-only `EVZ_NATIVE_NOTIFICATION_SOURCE_BLOBS_TOKEN`, an explicitly authorized source-site Netlify token, separate from all role credentials. Both canonical workspace and distinct encrypted credential namespace use that same bound private source site and token. This supports a public gateway where the private desk is protected by Netlify site-level SSO. The token may grant broader provider authority than these application checks; namespace-level least privilege and actual hosted authorization are not established. Never put it in source, logs, backups, client responses or role credentials.

The common gateway policy fields are `site_id`, `deploy_id`, `context`, `published`, `origin`, `policy_sha256`, `owner_credential_sha256`, `friend_credential_sha256`, `excluded_credential_sha256` and `credential_namespace`. The gateway reads `EVZ_NATIVE_NOTIFICATION_SOURCE_BINDING`, `EVZ_NATIVE_NOTIFICATION_MASTER_KEY_ID` and a protected 32-byte base64url `EVZ_NATIVE_NOTIFICATION_MASTER_KEY`; an optional previous key ID/value supports migration of encrypted records. Do not record keys, callbacks or secrets in source, logs, backups or issue text. No credential provisioning, runtime flags or protection changes are enabled by this document. Actual hosted gateway/source access, secret scope, native setup and device delivery need separate evidence.

## Desk setup controls

On an explicitly opted-in operations workspace, Setup shows the finite policy, saved usage allowance, paused state, subscription count and attempt counts without subscription credentials or callback addresses. With the separate admin flag enabled, the owner may record an actual observed included-usage percentage above the 30% reserve and a nonsecret evidence reference. The saved allowance ends at the earlier of 15 minutes after that observation or policy expiry. A current allowance is needed before subscribing and before unpausing in the desk. Pausing invalidates pending notification intents. Friend can read the bounded status but cannot access the owner controls. Policy mismatch requires the separately authorized rebind process. An ambiguous response requires refreshing saved status before another attempt. These controls do not create subscriptions, schedule dispatch or prove a device received anything.

## Protocol and recovery

The SDK endpoint exposes a role-filtered read-only status tool and the `operations.incident` and `operations.daily_summary` MCP Events. Payloads contain opaque IDs, generic categories, and for summaries a closed list of numeric counts plus day/generated time; no client names, source IDs, contact details or message bodies. Subscription arguments are empty and role comes only from the bearer credential. `events/subscribe` accepts webhook callback, secret, null cursor and optional `ttlMs`; lifetime is at most 24 hours and no later than policy expiry. It validates a signed one-time callback challenge, stages AES-256-GCM ciphertext in an immutable separate store, then activates the exact generation by canonical CAS. Failed/lost activation leaves an inert orphan. One role/event has one active callback. Refresh allows old/new signing secrets for five minutes; a third distinct secret during overlap holds. Unsubscribe revokes canonical authority first. Callback URLs must be public HTTPS, DNS answers must all be public, the TLS connection is pinned to a validated address and redirects are not followed.

Saved incident/digest projections add per-role outbox records in the same canonical write. Delivery reserves one exact event/body/subscription generation and unique claim under the existing conditional workspace authority. Each attempt consumes the configured daily/total budget; at most three attempts are permitted, with five- then fifteen-minute backoff, within the occurrence day and all expiry windows. 408/429/5xx and lost/timeout responses may retry only with the original event ID and exact body; 410 revokes the subscription and 413 holds the payload. The server checks binding, source, role, policy, subscription and deadline before/after awaited work and before the outbound connection. Native state mutations and credential staging also recheck their applicable authority around every Blobs SDK transport hop, including signed-URL requests; an already-started request can still finish late. Status checks the current source again before returning counts. Once a request starts it cannot be recalled; stale or ambiguous outcomes are held or uncertain. A callback 2xx means callback accepted only, never ChatGPT processing or a device notification.

The existing separately gated five-minute published operations clock can recover one expired claim or dispatch at most one callback per invocation only if `EVZ_NATIVE_NOTIFICATION_DISPATCH=mcp-events-v1`, the exact policy and a fresh included allowance are present. It uses the separate credential namespace and master key configuration above. Default builds emit no notification schedule. This clock is not immediate disconnect detection or an independent monitor for its own host outage. At full notification/outbox or workspace capacity, original source evidence remains saved and a hold/unsaved state is exposed; old history is not silently deleted. Remove the runtime flag and republish the default-disabled clock to stop dispatch; preserve all claims, callback receipts and uncertain history.

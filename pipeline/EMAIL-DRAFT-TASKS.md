The [task-only shared binding](#task-only-binding-and-common-authority) adds exactly bound proposal persistence; the distinct [shared review binding](#shared-adoption-and-content-review) adds signed adoption and separate exact content review. Historical/deployed task-only profiles retain their denials. No new connection or deployment follows from this source increment.

The original local increment prepares replies for fictional existing conversations in the loopback desk, including bounded approved PDF selection and registered conversation history. It invokes no model or provider itself. A separately authorized worker can retrieve one task and return one proposal without an operator session. The later finite native proof is recorded in [the implementation checkpoint](HYBRID-IMPLEMENTATION.md#verified-native-task-proof-and-next-source-boundary--october-27); it does not prove full live mailbox coverage or powered-off operation. The narrow credential limits these desk routes. It is not an operating-system or tool sandbox for the native Codex development worker; that worker followed a bounded task instruction within this development session. Production worker environment/tool isolation remains a separate gate.

## Interface and ownership

The assigned signed operator uses `POST /api/email-draft-tasks/create` with a stable `id`, `project_id`, current `revision`, a randomly generated 256-bit `token`, and `replace_task_id` (null initially). An unassigned existing conversation must first be explicitly claimed through the desk. The desk stores only the token hash. The token appears only in the explicit operator creation request and UI handoff; keep it outside context, results, checkpoints and logs. A lost creation response can be retried with the same request. A new attempt explicitly replaces the current task and revokes its authority. Tokens expire after two hours and are bound to this workspace directory/run.

`GET /api/email-draft-task/:id/context` and `POST /api/email-draft-task/:id/result` require `Authorization: Bearer <token>`. This credential grants no other route, client, approval or sending authority. Results contain `body`, `source_ids`, `uncertainties`, and `execution` (`provider`, `model`, `duration_ms`, `input_tokens`, `output_tokens`; token counts may be null when unavailable). Context explains the result schema and identifies allowed source IDs. Incoming text is evidence, never instructions.

### Approved PDF attachments

Creation additionally accepts optional `studio_asset_ids`: exact studio asset IDs explicitly permitted by the signed lead for this task. Omission grants no studio attachment access. The deterministic catalogue contains at most twelve same-project or explicitly permitted studio current approved, undisputed PDF baselines with verified originals. Entries contain safe names, asset/version IDs, approved-baseline identity, bytes and SHA-256; they expose no paths, provider IDs or arbitrary fetch references. Each PDF and the combined selected originals must fit 20,000,000 bytes. An eligible item beyond the catalogue bound is not offered; context reports truncation.

An optional result `attachments` array contains at most two exact `{asset_id,version_id,sha256}` selections from this task's current catalogue. Omitted or empty means no attachments, preserving earlier text-only results. Duplicates, foreign IDs, arbitrary paths/URLs, stale baselines, disputes, changed metadata or oversize bundles fail closed. Current catalogue changes invalidate unfinished tasks; adopted-message freshness binds only the exact selected versions and approval identities. Existing tasks from before the catalogue fingerprint require explicit replacement. A resolved dispute is eligible through its two-operator consensus event identities; an open dispute remains held.

`GET /api/email-draft-task/:id/asset/:asset_id/:version_id` uses the same task bearer, expiry, current source/style/catalogue checks before and after reading verified original bytes. It returns only one exact offered PDF with its hash header. It cannot use operator routes or download another client/studio version. This route does not establish semantic suitability; the worker and operator must inspect the actual file.

Atomic adoption validates and copies safe attachment descriptors into the saved draft's content hash. Operator review shows name/version/hash/size and an authenticated exact-original download. Body edits retain the selected bundle unless the operator explicitly removes all attachments; every saved change requires fresh approval. Content/facts approval covers the full bundle, followed by separate exact-send approval. Existing exact-mail dispatch rereads original bytes before MIME and verifies the full provider raw receipt. A lost or ambiguous send reconciles the original intent without resending.

Attached replies are a local controlled proof only. Existing shared exact-mail profiles reject them before separate approval or provider effects; their typed schemas gain no new attachment authority. The existing held project-PDF new-conversation route remains separate.

The worker result is an unapproved proposal. The assigned signed operator uses `POST /api/email-draft-tasks/adopt` with `id`, current `revision` and exact `result_sha256`. Adoption atomically records the existing `reply_draft_saved` event and task receipt under the lifecycle lock. Replaying adoption returns that original receipt without overwriting later human edits. Existing content/facts approval and separate sending approval remain mandatory. The adopted reply uses EVZ Digital Team; operator and worker attribution remain internal.

## Freshness and failures

Task context binds the current reply provenance, verified contact, assignment, restriction, stage, reviewed call facts, reply/discovery review, approved quote, existing draft and sender identity. Private notes are excluded. Unrelated notes do not invalidate work. A changed dependency holds context retrieval, submission and adoption. Adoption also checks the current revision. An obsolete/replaced/expired attempt cannot submit or adopt. Exact result retries reconcile by hash; different second results are rejected. No automatic retry starts execution or sends email.

Call claims require the exact operator-approved proposal, matching independent review and current transcript provenance. A later machine reassessment does not inherit human approval. Mismatched claims are marked unavailable, and retained evidence fingerprints invalidate affected drafts without rewriting their saved text. Upgrading an older task/draft that included call facts may therefore require fresh review.

The existing local signed incoming-sync caller may retain [bounded conversation history](GOOGLE-INCOMING-MAIL.md#local-retained-conversation-context). Task context exposes its exact ordered message bodies/provenance and permits only supplied `message:<id>` citations. Mailbox-sent text is historical context, never a desk approval, delivery receipt or independently approved client fact. Quoted text is untrusted content of its containing message. The task credential only reads retained state; it cannot refresh Gmail, select a route or submit source bodies. Operators can refresh through the enabled registered-source caller and inspect coverage/messages before task creation. Missing legacy history is explicitly current-reply-only outside the existing source hash. Actual retained history, pending changes and holds fence unfinished results/adoption and affected saved draft approval. Shared history/task execution remains unsupported.

The packet includes only the lead's [personal writing profile](CONVERSATION-OWNERSHIP.md), with an explicit default if none is saved. Its separate fingerprint holds unfinished work when that profile changes; the other operator's profile does not affect the task. A preference update preserves already adopted and reviewed wording. Handoffs retain wording but invalidate affected current-source authority. Tasks from before this fingerprint existed need explicit replacement; they are not silently upgraded.

The original contract supports controlled fictional local workspaces; historical generic and composed shared profiles still fail before task mutation. The separate task-only binding below adds typed task replay without adoption authority; only the explicit review successor adds signed adoption. Copying a local workspace into another directory invalidates its task credentials. The supported backup restore supersedes unfinished tasks even at the original path; proposal evidence is retained and fresh work requires a new task. Ordinary process restart preserves a task until expiry. Credential-shaped content and unknown fields are rejected at input/output boundaries; this check cannot guarantee arbitrary secret detection or semantic truth, so operators must review the exact proposal.

# Disabled direct business Calendar transport

`google-calendar.mjs` adds a separately disabled direct REST transport to the existing [guest-confirmed booking lifecycle](CALL-DESK.md). The current source accepts only the controlled fictional shared preview and `.invalid` guests. `EVZ_OPERATIONS_GOOGLE_CALENDAR` and the separate Calendar owner OAuth capability are unset. No Google call, actual consent, invitation, hosted configuration, production activation or computer-off proof was performed.

## Supported signed caller

The existing `/desk` handler supplies ordinary business work to either signed operator, with current same-origin session/CSRF protection:

- `GET /desk/api/calendar/availability` reads the configured primary calendar and bounded eleven-day FreeBusy range, then uses existing Eastern meeting-slot rules. Returns controlled fixture status, slots and check time.
- `POST /desk/api/calendar/queue` takes `{revision,prospect_id,attendee_email,recipient_confirmed,slot_agreed,start,end,timezone,title,description,location,mode}`. Use explicit RFC3339 dated times, `timezone: "America/New_York"`, an existing interested fictional contact, title beginning `EVZ Digital`, and `mode: "video"` or `"phone"`. Location is exact optional text; no participant/address is invented. This checks live-wire-shaped injected availability before calling existing `queueMeeting`. It returns `{queued:true,booked:false,booking_id}`. This is a reservation, not an invitation receipt.
- `POST /desk/api/calendar/dispatch`, body `{booking_id}`, uses that exact signed confirmation and durable existing `operations.requests[booking_id + "-create"]`. It checks availability before intent reservation and again immediately before the create claim. One insert is attempted after the confirmed CAS claim. A repeat dispatch returns the saved status and reconciliation instruction.
- `POST /desk/api/calendar/reconcile`, body `{booking_id}`, reads only the reserved event ID. It never lists/searches or inserts. A successful exact event populates existing `operations.bookings`, `operations.effects` and provider-only `meeting_verified`; repeated reads update the attendee status without another effect event or invitation. Each safe read claims the existing request with CAS; a newer explicit read supersedes an older finalizer, which cannot overwrite its receipt.

Both roles can approve ordinary business work. The approved assignee retains the exact confirmation; switching the current conversation owner, contact, call/reply/discovery context or configured grant/calendar requires review and cannot silently reuse that approval. Source changes never erase an uncertain intent. Account connection remains owner-only.

## One existing authority

The existing `queueMeeting` still owns the guest/slot/title checks and stable `meeting-*` identity. Its local controlled simulation and production connector behavior remain supported. For this hosted path, existing `operations.bookings` in the same workspace configuration holds the exact confirmation, policy/context hashes and signed `meeting_queued` event. The conditional store passes its current configuration to the existing change callback, saving configuration and state in the same CAS envelope. Failed or uncertain CAS never reruns the callback or any provider effect.

There is no second booking queue. The existing creation request ledger, verified booking map and provider effect event remain the authority. A reserved business cannot choose a second slot. Other internal reservations also block overlapping slots/buffers. A stable 65-character lowercase hexadecimal event ID is derived from run and booking identity; it satisfies Google's [base32hex event-ID rules](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert). The ID and exact intent hash precede insert. The private intent marker is read back from the event as well as the ID/content.

Timeout, 409, missing event, mismatched event, failed CAS or lost acknowledgement retains the existing intent. There is no automatic retry, lease reclamation, alternate calendar, query search, cancel, reschedule or invitation permission API. An intent that never reached insert can still remain held; operator reconciliation does not grant a second create. Existing local connector authority is never used as a fallback.

## Exact provider boundary and honest receipts

Only the fixed Google Calendar v3 host and four operations are supported: [primary calendar metadata](https://developers.google.com/workspace/calendar/api/v3/reference/calendars/get), [FreeBusy](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query), [insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) and [exact event get](https://developers.google.com/workspace/calendar/api/v3/reference/events/get). No redirects or request retries. JSON is streamed with a 100 KB limit; each request has a ten-second deadline and a dispatch/reconciliation chain shares a forty-second HTTP deadline. The default-disabled scope still needs actual hosted latency/compatibility proof.

Before reservation/insert, verified OIDC grant account and `calendars/primary` metadata must identify `ensizziyo@evzdigital.studio`; the returned canonical calendar ID and Eastern timezone must match the private policy. FreeBusy addresses that exact ID, covers the entire slot plus fifteen-minute buffers, and must return exactly one complete calendar without errors/groups/paging. Existing `validateBookingSlot` uses UTC instants and IANA `America/New_York` formatting, preserving weekday 9–5, twenty-minute duration, past-date rejection and DST behavior. Internal reservations are CAS serialized. Google FreeBusy and insert are separate operations, so an unrelated external user can still create a conflicting event between them; this is not an atomic provider reservation.

Insert requests exactly one guest, the approved summary/description/location, Eastern start/end, private/opaque visibility, reminders off, guest editing/inviting off and `sendUpdates=all`. Video intent uses `conferenceDataVersion=1` and one stable Meet create-request ID. The exact owner organizer is independent of the approved Gmail sender alias; `hello@evzdigital.studio` is never substituted as organizer.

Full event readback checks exact ID/private marker, organizer/self/calendar request, single guest, exact content/location/timezone/instants, private/opaque/reminders, no recurrence or truncated attendees, and known attendee response. Video requires conference success and the actual Meet entry point; pending/failed/missing conferences stay held for exact-ID readback. Phone intent cannot acquire a video conference. The existing `bookingIdentity` accepts a small conversion from Google wire `useDefault`/`self` into the existing connector spelling.

`Verified` means exact event readback. `invitation_delivery: "Unverified"` remains explicit because insert/sendUpdates does not establish delivery. `guest_response` records Google's separate `needsAction`, `tentative`, `declined` or `accepted` value. The application never writes an accepted response into the request. Event creation is not a claim that the guest received or accepted an invitation. See the official [event response/conference fields](https://developers.google.com/workspace/calendar/api/v3/reference/events).

## Future separate owner consent profile

Explicit `calendar-booking-v1` reuses the existing [owner OAuth state machine](GOOGLE-OAUTH.md): one-use session/state/PKCE/nonce, verified signature/business identity, independent encrypted credential envelope, refresh CAS and local disconnect. Its callback is `/desk/api/google-calendar-oauth/callback`; `/start`, `/callback`, `/disconnect` are owner-only and `/status` is metadata-only for both roles. The existing Gmail default and Drive read-only profiles keep their exact scope sets and storage bindings.

This future profile requires exactly OIDC `openid` and `userinfo.email` plus `calendar.freebusy`, `calendar.events.owned` and `calendar.calendars.readonly` under `https://www.googleapis.com/auth/`. The official [FreeBusy scope table](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query) accepts the first Calendar scope and [owned-event methods](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) accept the second. Neither authorizes `calendars.get`; its official table explicitly requires the minimal `calendar.calendars.readonly` metadata scope. That source-based decision was sent to the parent before adoption. No CalendarList, ACL, general Calendar write or management scope is requested. These scopes are broader than one calendar at Google's consent boundary; the exact business-primary restriction is enforced by the application.

Future placeholders only, not installed configuration: `EVZ_OPERATIONS_GOOGLE_CALENDAR_OAUTH=owner-calendar-code-v1`, `EVZ_CALENDAR_OAUTH_BINDING`, `EVZ_CALENDAR_CREDENTIAL_NAMESPACE=evz-calendar-credentials-<fresh-reviewed-suffix>`, `EVZ_CALENDAR_CREDENTIAL_KEY_ID`, `EVZ_CALENDAR_CREDENTIAL_KEY`, `EVZ_CALENDAR_CLIENT_SECRET`. Binding has the existing tenant/site/deploy/origin/account/audience fields with a distinct new Web client and exact Calendar callback. Namespace, 32-byte key, client and secret must be independent of Gmail/Drive; no credentials are copied. External Testing retains the existing seven-day maximum. Real project/API enablement, app/admin classification, grant lifetime, secret scope/logging and fresh owner consent require later review.

A later controlled source configuration would explicitly bind `google_calendar: {enabled:true,capability:"fictional-calendar-v1",run_id:"<exact-fictional-run>",account:"ensizziyo@evzdigital.studio",calendar_id:"ensizziyo@evzdigital.studio",grant_id:"<new-exact-calendar-grant>"}`, existing Calendar slot policy, and the separately disabled transport flag `EVZ_OPERATIONS_GOOGLE_CALENDAR=fictional-calendar-v1`. Connection alone starts no Calendar reads or invitations. Production and D2 notes-only remain closed even with these source flags.

## Verification and rollback

From `pipeline`, run `node --test google-calendar.test.mjs`, `npm run check` and `node --test --test-concurrency=1`. Tests exercise signed owner/friend handlers, real local loopback HTTP with documented wire shapes, actual RSA OAuth-to-Calendar token wiring, exact reservation/intent/event/readback, availability drift/buffers/DST/past dates, stale contact/context/grant, malformed/partial/paged/oversized responses, concurrent claims/CAS failure/lost acknowledgement, timeout/409/missing/mismatched readback, conference/attendee status and one intent/event. Existing inert-route tests cover the new paths. Intercepted desktop/narrow browser proof verifies the actual Calendar callback HTML/JS, query scrubbing, Strict-cookie return, friend denial, keyboard return and no console errors. Nothing calls real Google.

Rollback with flags unset removes the new caller/transport/profile. Preserve confirmations, request intents, effects and event IDs. Never give an uncertain invitation to an older sender for replay. No production merge, migration, actual hosted/provider invitation/guest-acceptance, remote device or computer-off acceptance follows from these local proofs.

# Disabled hosted Gmail incoming synchronization

`google-incoming-mail.mjs` connects the existing business Gmail grant to `reply_received`, source-bound reply preparation, cold-contact stop and held team notification preparation. It reuses current project/contact/thread associations and the lifecycle reducer. There is no second queue, inferred positive interest, conversational send, Gmail draft, read-state modification, deletion or notification delivery.

## Supported caller and scope

Both signed operators may POST `{}` to `/desk/api/incoming-mail/sync` using the existing same-origin session and CSRF token. GET `/desk/api/incoming-mail` returns cursor, progress and holds without tokens or message bodies. `syncIncomingMail(app,{actor,env,getAccessToken,fetcher})` is the source caller; injected HTTP/token boundaries support local verification. The hosted handler supplies the existing encrypted OAuth token provider when its separate grant capability is configured. Connecting Google alone starts no reading.

The independent **unset by default** flag is `EVZ_OPERATIONS_GOOGLE_INCOMING_MAIL=fictional-incoming-v1`. Private `google_incoming_mail` config separately needs `enabled:true`, `capability:'fictional-incoming-v1'`, existing `run_id`, explicit `grant_id` and `account_email` matching `sender.account_email`; sender remains `hello@evzdigital.studio`. This candidate accepts only controlled fictional `.invalid` contacts. Production and D2 notes-only reject synchronization. No environment/account settings were changed and no credential example was added.

The grant contract is unchanged: exact `gmail.readonly` + `gmail.send`, optionally existing essential OpenID email identity scopes, exact account/grant/expiry and profile readback. Reading needs no broader permission or send-as settings. OAuth remains owner-managed; ordinary business work is available to both operators.

Routes come only from existing `config.operations.threads`, retained `operations.email[*].thread`, or a verified exact-mail action's delivery receipt and approved package. Email actions explicitly marked `payload.internal_notification === true` are excluded before either retained-thread or receipt derivation: owner/friend notification conversations are outside prospect monitoring. Their original action, intent, MIME, receipt and sender reservations remain intact. Missing prospect IDs or malformed actual prospect routes still fail validation. Each route must match its project and current verified contact. A thread shared by different projects/contacts fails closed. Subject alone never registers or attributes mail. Changed route/contact/grant registration holds the prior cursor without resetting or inheriting coverage; reinitialization needs separate review.

## First sync, progress and recovery

First sync obtains `users.getProfile.historyId` **before** reading registered threads. Successive signed calls read one complete registered thread each, including every retained incoming reply after its registered original Sent message. It then catches up through `users.history.list` from the pre-scan history ID, covering arrivals during initial reading. It never lists or reads the whole mailbox. Mail outside registered conversations is outside this bounded contract; unrelated history additions are counted without fetching or attributing contents.

Each invocation performs one profile GET plus either one `threads.get?format=full` or one history-page GET. Initial/resync scope is 1–12 registered threads, fewer than20 messages per thread and at most2,000,000 response bytes. History pages contain at most50 records,100 added/100 deleted messages and250,000 response bytes. At most20 continuation tokens are retained; loops/excess hold. A page's registered message IDs/thread work are saved before its reads, then processed one thread per invocation. The original cursor stays fixed across pages and advances to returned `historyId` only after the final page and every associated effect are persisted. Decimal history IDs are compared as integers without floating-point loss.

The existing conditional store commits lifecycle events, stops, notification preparation, message/source dedup and cursor/progress together. The existing reducer runs against that prospective state; HTTP never runs inside CAS. Revision or exact-configuration conflicts commit none; the configuration fingerprint is checked inside the conditional transaction. After a lost committed response, the next strong read recovers progress; safe GETs may repeat while stable message/source event IDs prevent duplicate lifecycle effects. Dedup holds1000 distinct message/project pairs; source revisions retain old lifecycle events. Existing20MB/20,000-event limits still apply. History is never silently evicted.

History404 persists an **expired-history gap hold**, restarts a capped scan of registered threads and catches up from a fresh pre-scan history ID. Previously ingested sources deduplicate. Messages known from history or retained provenance that disappear before full read, including known source-deletion history, hold without advancing past the gap. Deleted mail cannot be reconstructed. The gap hold remains visible after catch-up; this source supplies no shortcut for clearing it or restoring contact. An operator must review original-mailbox coverage and retained state before separately reviewed recovery. Other provider/parser failures retain the cursor/pending work, prepare attention and pause registered cold routes; successful reads never resume them automatically.

## Attribution and MIME provenance

Original Sent mail must match registered Gmail thread/message IDs, sender, recipient, subject, RFC Message-ID and retained time bounds. Incoming sender/recipient must match current contact/business alias and reference a business Sent RFC Message-ID in that thread. Cc/Bcc, alternate Reply-To/Sender, duplicates, invalid chronology and changed thread associations hold. Authentication requires a single Gmail `mx.google.com` Authentication-Results with one passing DMARC result aligned to sender domain. Missing, duplicate, failed or unsupported authentication holds. This is a conservative provider-source check; it does not establish a human author's identity or commercial authority.

`replyContent` consumes Gmail's parsed full payload and base64url body data; Gmail has already decoded MIME transfer encoding. The bounded reader supports nested multipart/alternative, plain UTF-8/ASCII and conservative HTML-only text projection. Plain/HTML alternatives do not become separate replies. It preserves supported full text, MIME-payload/body/source hashes, Gmail/RFC identities and references, sender/recipient/subject, provider internal date, original Date header and complete payload source hash. Quotes/signatures remain in provenance while the existing extractive starter removes recognizable history. HTML never renders or follows links. Unsupported charset, malformed/partial/externalized body, ambiguous text, excessive tree/headers or more than24,000 text bytes holds without truncation or guessed decoding. Attachment bodies are never fetched or interpreted as reply instructions.

Outgoing, drafts and self mail do not become human replies. Standard Auto-Submitted/list/precedence/autoresponder headers and delivery-status/bounce signals produce existing held automatic/bounce dispositions. Refusal/automatic wording conservatively withholds a starter; it never establishes positive interest. A verified reply pauses cold release through the existing lifecycle, exposes human review and prepares a responsible-operator notification with delivery held. Current body/provenance corrections supersede stale drafts, reviews and approvals through that same reducer. No model or semantic-quality claim is made.

Complete project G1 includes registered originals, authored source/runtime/PDF and substituted raster evidence alongside incoming provenance and internal MIME/intents; restore remains disabled, with route discrimination rechecked only after a test-only fictional trusted rebind. Raster substitution verifies recovery integrity, not visual quality. Run `npm run check` and `npm test` from `pipeline` for the full source checks.

All runtime provider traffic is substituted locally. No real Google profile/list/read/token/consent, credential read/copy, mailbox import, production activation, scheduler, external alert or send occurred. Actual hosted latency/cost, grant/mailbox compatibility, expired-history recovery, independent device access and computer-off operation remain unverified. This is a manual signed source caller; no polling interval or immediate alert delivery is established. Rollback is leaving the flag unset and preserving cursor/events/provenance for review. OAuth and exact-send remain independently gated.

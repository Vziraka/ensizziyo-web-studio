No result from this source check permits a retry of an existing send.

## Durable intent and uncertain outcomes

Before original-byte retrieval or any Gmail/token request, dispatch reserves stable `${action.id}-intent` in `operations.requests`. The combined daily count includes previous native intent/send and information-sender reservations; provider quota is not send authorization. The intent stores the immutable package/binding, reservation date, deterministic RFC Message-ID and then bounded exact encoded MIME/hash. Current source, contact, stop, ownership, exact approval and configuration are rechecked before claiming dispatch. CAS callbacks only mutate state; no HTTP effect runs inside one.

The dispatch claim is durably **Uncertain before POST**. The initial claimant may POST once. A lost response, process exit, state-write uncertainty, 401/token expiry, quota/error response, hosted invocation retry or repeated caller invocation cannot issue another POST. A reservation whose MIME or preflight failed remains held and cannot be automatically reclaimed. An unconfirmed reservation write also cannot reach Gmail. The earlier plain-text information sender rejects pending exact-email approvals/intents, and native automation excludes these actions.

`reconcileExactMail` reads the saved intent, never regenerates a revised message. Known success fetches that provider ID as `format=raw`; unknown outcome searches Sent by `rfc822msgid:<deterministic ID>` and follows at most3 pages/10 unique candidates. It requires exactly one complete match. Empty, ambiguous, duplicate, truncated, looping, mismatched or unavailable results retain **Uncertain**, without resend permission. Complete routing headers, date, subject, Message-ID, reply headers, MIME structure, full decoded body and every attachment filename/type/byte count/SHA-256 must match. The same action receives the sender readback receipt. A deterministic Message-ID is a reconciliation key, **not Gmail idempotency**. Sender Sent readback does not establish recipient delivery.

## Real provider and credential boundary

`googleHostedTransport({getAccessToken, fetcher, account, grantId})` uses documented Gmail REST paths for profile, send-as aliases, fresh thread/source reads, `messages.send`, Sent search and raw message readback. Fetch has a25-second deadline, rejects redirects, bounds streamed JSON and performs no automatic retry. It does not call an OAuth SDK request method capable of refreshing and resubmitting a send. The server-owned token callback may obtain/refresh access before a request, but cannot retry the Gmail POST. Tokens/errors containing provider secrets are not copied to lifecycle records, backups, logs or output.

The token boundary requires the new owner grant/account/ID, unexpired access token and **exactly** `gmail.readonly` plus `gmail.send`, optionally accompanied by precisely the essential `openid` and canonical `userinfo.email` identity scopes used by the new owner grant. Preflight requires `profile.emailAddress` to match the configured business owner and one `sendAsEmail:hello@evzdigital.studio` with `verificationStatus:accepted`. The official send-as list contract currently accepts `gmail.readonly`; a missing scope, 403 or unavailable alias holds with a precise grant/access requirement. The code never expands to `mail.google.com`, modify or settings scopes. Existing connector/CLI/service-account credentials are not a source for this boundary.

The new [OAuth source contract](GOOGLE-OAUTH.md) implements owner-only code/offline start/callback/status/local disconnect, exact expiring session/state/PKCE/nonce, verified returned identity/scopes, encrypted isolated storage and refresh/invalid_grant handling. Organization/client/API/admin/app-type checks, real consent, deployment/secret setup and live proof remain separate. No local token copy, hosted environment write, permission change or consent occurred.

## Bounds, verification and remaining work

The adapter independently caps attachments at20,000,000 original bytes total, encoded MIME at28,000,000 bytes, decoded body at32KB, two PDF attachments, and raw-read JSON at38,000,000 bytes. The hosted fictional workspace's existing2MB CAS envelope can impose a **lower** limit because encoded MIME is retained durably; failure occurs before a Gmail request. That store is not enlarged by this task. Input JSON/background payload limits are not a provider upload entitlement. The known30,591,178-byte original is held and needs a separately approved immutable Drive-link and named-recipient sharing/readback route; no public share, upload, compression or silent link substitution exists.

The MIME composer emits a deliberately narrow UTF-8/base64 text/PDF subset, safe fixed filenames, bounded RFC headers and encoded non-ASCII subjects. Readback accepts that subset and holds unsupported provider rewrites; actual tenant wire compatibility is unproved. Fresh thread reads require fewer than20 complete chronological messages and a2MB response; a changed/later reply or sent message blocks dispatch. The read/send race at the external mailbox cannot be atomic; source/stop are checked immediately before the POST claim, and later changes retain the existing uncertain/reconciliation behavior.

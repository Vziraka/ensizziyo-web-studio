# Automatic mailbox intake

`shared-mailbox-clock-v1` extends the existing mailbox review and proposal workspace with scheduled read-only intake. Existing capabilities remain unscheduled. The same canonical workspace retains records, manual call outcomes, ownership, PDFs, tasks and exact draft approvals. The worker never classifies messages, assigns new responsibility, generates proposals or sends mail.

The immutable `mailbox_clock` policy binds the published desk deployment, cadence, recovery generation, expiry, at most three reads per tick, a daily read ceiling and a deadline no longer than 25 seconds. Either signed operator can pause or resume. Initial state is paused and has no allowance. A separate reviewed allowance records included-usage evidence, expiry and a finite total read budget. Failed and uncertain reserved reads consume that budget. This is a finite authorization, not a live meter or proof of a percentage usage reserve; unknown hosting allowance remains a release hold.

Every invocation claims the current schedule slot conditionally, then reserves each provider read before making it. The saved tick and monotonic fence prevent duplicates and concurrent ticks from repeating a reserved read. A late provider response cannot commit after pause, allowance replacement, deadline, policy change or a later tick. Observation/failure and step settlement share one conditional write and independent replay. Lost acknowledgements reconcile only the exact saved envelope. An unresolved read stays charged; the next scheduled slot resumes the durable Gmail cursor instead of restarting bootstrap. Expired Gmail history requires explicit recovery.

Incoming profile, list, history and message methods accept an optional internal `beforeFetch` callback. Clock intake supplies its current source/step guard: after awaited token/current-grant preflight, one fresh validated envelope supplies both state and config, then trusted time verifies the exact live allowance, tick, fence and pending step before GET. The transport bounds that callback and rechecks abort/token synchronously before fetch. It runs once per provider request, not once per response chunk; ordinary callers omit it. A preflight pause or drift denies GET without refunding the already-reserved step. A later pause still rejects result settlement. This is a final action-time read fence, not an atomic transaction spanning storage and Gmail.

## Hosting

### Explicit production package

`production-mailbox-clock.mjs` supplies a separate production entry generator. `productionMailboxClockEntry()` emits only a disabled handler with no schedule; the existing generic entry and manual callers are unchanged. A reviewed nonsecret input must contain exactly `{binding,oauth,credentialNamespace,clockPolicy,starts_at,expires_at}`. The binding is an exact `shared-operations-desk-v1` manifest; `clockPolicy` is the full schema2 policy with matching site/deploy/origin. OAuth uses the existing closed production mailbox identity, full binding hash and mailbox-policy hash, canonical callback and separate credential namespace. The canonical envelope must match both policy hashes on every workspace read. Invalid or extra fields fail preparation.

For an explicitly supplied input, the generated bytes import `../production-mailbox-clock.mjs` from `pipeline/netlify-functions` and export the cadence's UTC cron. Runtime additionally requires `EVZ_PRODUCTION_MAILBOX_CLOCK=finite-intake-v1`, exact trusted published production context and canonical request origin. Only `EVZ_PRODUCTION_GOOGLE_CREDENTIAL_KEY_ID`, `EVZ_PRODUCTION_GOOGLE_CREDENTIAL_KEY` and `EVZ_PRODUCTION_GOOGLE_CLIENT_SECRET` are projected to the existing OAuth runtime. Legacy Google variables, operator/session keys and arbitrary ambient environment are not forwarded. No credential values enter generated source. The wrapper uses the actual encrypted-grant/read/refresh path, not a synthetic token provider.

The immutable canonical UTC window must satisfy `starts_at < expires_at <= clockPolicy.expires_at`. Before that window or after expiry the handler denies before secret projection, storage or provider access. Each admitted invocation ends at the earlier of 25 seconds or window expiry. Storage factories/methods and default SDK HTTP hops, OAuth and incoming transport recheck this bound; transport signals retain any narrower existing abort signal. The host's optional `invocationDeadline` clips the existing tick/settlement execution budget. A late response cannot settle; reserved uncertain reads remain charged. This does **not** limit the number/cost of public invocations, bound whole scheduled-host overhead, remove a cron, or establish actual scheduled-request metadata. Disable/remove the deployed schedule after the finite proof; paused or expired functions still incur invocation cost.

The focused production tests execute emitted bytes with the actual SDK, clock and encrypted OAuth grant against fictional network/storage boundaries. They establish source packaging behavior only. A separately reviewed history-compatible private preparer, exact source/dependency/ZIP/function/schedule profile, current grant/config binding, fresh included-capacity evidence, real request/deadline/latency measurements and finite shutdown receipt remain deployment/activation gates. No default build is switched to this entry and no schedule is deployed by this source change.

Netlify schedules run on published deployments, not deploy previews, and have a 30-second execution limit. Keep the operations project protected; the public studio and API-only proposal gateway do not receive Gmail credentials. A new published deployment needs its exact manifest and Google grant binding reconciled deliberately. Existing protected previews are retained until cutover is verified.

The build emits a scheduled function only with `CONTEXT=production`, `EVZ_MAILBOX_CLOCK_BUILD=shared-mailbox-clock-v1` and an allowed `EVZ_MAILBOX_CLOCK_INTERVAL_MINUTES` of 5, 15, 30 or 60. The runtime additionally requires `EVZ_MAILBOX_CLOCK_RUNTIME=shared-mailbox-clock-v1`, the exact manual binding and trusted published Netlify context. Default and preview builds emit only a disabled response. Build/runtime cadence must match the saved policy. Creating source or deploying a preview activates nothing.

Measure actual store/provider latency and included Netlify usage before choosing a production cadence. The current workspace is roughly 12 MB; repeated whole-workspace reads and writes are material. The finite fictional proof cannot establish sustained affordability or 100-business/day capacity. A paused scheduler still incurs invocation/validation work, so disabling its build/runtime is the operational stop for hosting usage.

The host validates one canonical envelope before returning a paused/expired hold. An active invocation retains fresh conditional guards. Instrumented empty-history fixtures require 12 workspace reads and three writes with either one or four provider response chunks; paused/expired invocations require one read, and duplicates four. These counts measure internal storage operations, not billable bandwidth. A finite provider-read allowance does not bound scheduled hosting overhead. The first hosted proof must use one total read and disable its schedule after readback.

The current generic upgrade recipe rejects clock history; do not clear it or treat it as absent. Exact production OAuth wiring, function/schedule allowlists, fresh included-capacity evidence, measured deadlines and a finite schedule removal/disable receipt are additional activation gates. Keep the independent operations-health/preparation cron off until its total write/tick overhead is bounded. Missing postal details affect commercial activation only; manual/noncommercial intake and source verification remain available.

## Retained history and signed rebind

Explicit `mailbox_clock.schema_version: 2` uses the same closed immutable policy fields and finite expiry/bounds as version1. It adds no scheduled function. Policy1 keeps its previous behavior and rejects state2. Policy2 can inspect exact retained state1/state2 under a changed policy, but legacy, mismatched or restored controls cannot execute until reviewed rebind. Imported history stays unchanged before that signed decision.

State2 extends the existing clock ledger with only `policy_history` (at most20 prior identity receipts), `retired_ticks` (at most1000 exact retired tick receipts) and `recovery_required`. Allowance/day charges remain the only charge ledger. Rebind archives the current tick, including pending step and settlements, with its original policy/mailbox/recovery identity. It preserves allowances/used steps, days, global last slot/fence, cursor, pause record and unrelated client/work/send history, then stays paused with no current tick or allowance. A nonzero fence with no current tick requires its exact latest archived receipt. Next-slot rollover also archives an expired unresolved state2 tick before replacement; archived ticks never become executable pointers or additional charges. Old completed receipts that were never recorded cannot be manufactured.

Either signed operator may POST `/desk/api/mailbox-clock/rebind` with closed `{revision,previous,current,authorized:true}`. `previous` is `{schema_version,policy_sha256,mailbox_policy_sha256,recovery_generation,recovery_required}`; state1 projects recovery-required as false. `current` is `{config_sha256,policy_sha256,mailbox_policy_sha256,recovery_generation}` from the current server status. The server verifies both against retained controls and the immutable reviewed configuration under the authenticated binding. It changes no settings. Require current revision, paused controls, an unexpired target policy and elapsed original deadline for an unresolved tick. A revoked restored Running tick is historical evidence, not live authority. Stale identities, unpaused/live work, exhausted history or archive collision fail before partial changes. Safety pause-true remains available after expiry or at valid history capacity.

After rebind, save a new unique included-only finite allowance with evidence no older than15 minutes and expiry within policy, then explicitly resume separately. Old grant IDs, slots, fences and delayed results cannot be reused. Historical limits/expiry may exceed a lower new cap; those records remain readable, while new actions count all retained daily consumption. No history is pruned to obtain capacity. Status and Setup expose the restore/rebind hold, permanent charges, unresolved archives, current limits and separate budget/resume controls. A runtime flag does not establish that a schedule was deployed. The ordinary reserve is30%; record an explicitly authorized continuing task override in the evidence reference rather than claiming an automatic usage meter.

Complete backup capture/read and inert shared snapshot preserve source state exactly. **Disaster restore** deliberately revokes clock authority: it upgrades state1 controls to state2, pauses, clears the active allowance pointer and sets recovery-required, while retaining original tick/status/settlement bytes, charges and archives. Even identical old policy bytes cannot resume that authority. Signed rebind, a fresh unique budget and separate resume are required. Keep this revoked projection distinct from an exact canonical-state witness. Source pause/drain/retirement must also stop any different old deployment before a real migration; target rebind cannot stop it remotely.

Conditional writes replay exact typed transitions and check current deadlines/binding again at the pinned SDK lookup/data-PUT boundary through the existing transport guard. An expired or changed local authority blocks data PUT; a competing remote ETag fails the conditional write and preserves the other edit. There is no automatic replay after conflict/uncertain acknowledgement; only exact saved-envelope reconciliation establishes success. The clock host default store uses the same guarded fetch as the desk.

Run `node --test mailbox-clock.test.mjs mailbox-clock-host.test.mjs mailbox-clock-history.test.mjs` for legacy/history/capacity, both signed handlers, complete/inert/disaster recovery and actual SDK latency/binding/CAS coverage. The fictional browser fixture uses actual handlers/UI, both roles and a one-shot fake tick, including a separate same-policy restored Running lane. It is not a hosted or PC-off proof. Before production activation, a separately reviewed compatible preparer, exact OAuth wrapper/function/schedule profile and finite host-overhead/shutdown proof remain required; existing frozen recipes are not broadened. Postal details hold commercial sending activation only, not desk software, automatic intake, research, saved status or controlled noncommercial end-to-end testing.

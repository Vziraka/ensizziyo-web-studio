# Private asset references and approved versions

The **Assets** view keeps studio-wide and project-linked file references in the existing private lifecycle state, outside Git. Project references can be added at any sales stage. The index records metadata and operator choices; it does not copy or fetch file contents.

Use a Google Drive file ID as `drive:<file-id>` or a path relative to the authorized private storage root as `private-path:<relative-path>`. Do not paste sharing tokens, credentials, absolute computer paths, or file contents. Give each version a distinct reference. The app cannot verify that a Drive item is immutable or that the referenced file still exists.

Registering a new version never replaces the approved baseline. Either signed operator can approve an uncontested version, and that approval takes effect immediately. A new approval clears the other operator's older selection from the current view; the append-only event history retains it, but it cannot count as a current objection.

Use **Flag disagreement** when an operator explicitly objects to a different version. The last approved baseline stays active while the disagreement is open. Each operator must make a fresh choice within that disagreement; when both current choices match, that version becomes the baseline. A selection from before the disagreement does not count toward its resolution. Event IDs and revision checks preserve attribution and reject stale writes. These are internal asset-reuse decisions, separate from client approval of a proposal or delivery.

This is a reference index, not connected retrieval: no Drive read, permission check, file hash, or cross-device synchronization is performed. Remote authentication, shared hosting, and automatic asset retrieval remain open acceptance criteria.

**Save design feedback** retains either operator's exact direction, source asset/version, date and scope. Project is the default; a project asset defaults to its own record. A studio asset needs an explicitly selected project for project feedback. Choose **Explicit studio-wide direction** only when the operator intended broader reuse. Feedback is recorded separately from file approval and never changes an approved baseline or resolves a disagreement.

Use **Continue a project → Project context** to recover that project's assets, its feedback and explicit studio-wide directions. Every direction shows the original version reference and operator, including feedback on a draft or older version. The newer draft remains a draft until approved through the existing choices. Filtering keeps unsaved form entries in place. A studio-wide direction can cite a source belonging to another project, and both operators retain the already-agreed visibility of all client work.

This increment records explicit feedback and makes it retrievable in the local desk. It does not infer patterns, turn ambiguous comments into standards, apply changes to a design, detect semantic contradictions or pass context to a remote AI tool. Review competing directions and use the existing disagreement control for a contested asset change; the baseline stays active until the agreed resolution. Automatic preference interpretation and task-workflow retrieval remain open.

The `asset_feedback_added` event uses the same signed operator, expected revision and append-only event interface as approvals. It requires a registered source version, bounded text, and an existing project unless studio scope was explicitly chosen. Duplicate events do not add another entry. Existing indexes acquire a feedback list only when used; no migration rewrites previous versions or choices. Rolling back this view leaves retained private feedback and events intact.
